# AI-Native Development Policy

In this repository, autonomous agents and generative AI tools are fully integrated into our standard engineering workflow. Every pull request is assumed to have been authored or assisted by AI. Because velocity is high, our policy focuses entirely on validation, systemic guardrails, and human-in-the-loop accountability.

## 1. The Validation Prerequisite
Since every PR is agentic, no individual AI disclosures are required. Instead, every submission must pass our strict validation stack before it can be merged.
* **Hermetic Testing:** Any PR introducing code changes must include corresponding automated tests (unit, integration, or end-to-end) that execute cleanly in CI.
* **Deterministic Execution:** Agents must not commit code that "should work." The human operator or orchestrator must run the code locally or in a sandbox to verify functional correctness.

## 2. Reviewability over Transparency
Because agents can generate large volumes of code instantly, the primary constraint on this repository is reviewability.
* **Atomic Submissions:** PRs must be strictly limited to a single logical change, refactor, or feature. If an agent refactors an entire file while fixing a bug, split them into two separate PRs.
* **Human Comprehension:** The human merging the PR is responsible for the code. If you cannot explain the agent's logic or architecture to another engineer, do not merge it.

## 3. Documentation and "Agent Fluff"
AI agents frequently generate overly verbose markdown, redundant code comments, or hallucinations in documentation.
* **No Inline Novelty:** Do not allow agents to write paragraph-long explanations for self-documenting code. Code comments must be sparse and strictly focus on *why* a complex architectural choice was made, not *what* the code does.
* **Strict Fact-Checking:** Documentation, setup guides, and API schemas generated by agents must be manually verified. Broken links, hallucinated CLI flags, or non-existent dependencies will result in immediate PR rejection.

## 4. Dependency and Security Guardrails
Agents frequently pull in external packages or write patterns prone to common security vulnerabilities.
* **Dependency Lock:** No agent may introduce a new third-party dependency without an explicit architectural sign-off from a human maintainer. 
* **Automated Linting:** All PRs must pass static analysis, security scanners (e.g., SAST tools), and linter rules defined in our CI pipeline.
